Guardian — notes, dev by dev

Software Supply Chain Guardian: an agentic AI system that discovers what an application is built from, detects vulnerable and suspicious components, prioritises them with an explainable score, proposes a safe fix, waits for a human, then validates the fix in a Docker sandbox and reports the evidence.

Big picture

The whole system on one page

Five roles, one pipeline. Every box below is coloured by the role that owns it (Dev1–Dev5, as defined in GUARDIAN_PLAN.md and the README's Contributors table). Facts come from tools; the LLM only reasons over stored evidence; a human approves every change.

Dev1 · agents, orchestration, LLM, guardrails Dev2 · tools, graph, sandbox Dev3 · UI & API Dev4 · intel, scoring, detectors, reports Dev5 · targets, QA, docs

Dashed line: the target repo is never modified — work happens on copies under runs/<id>/. Dev3's UI/API reads the store and posts approvals back to the gate.

Tools = facts

Syft, Grype, OSV, detectors, registry/EPSS/KEV lookups create Evidence. Only tools can create evidence — never the LLM.

Agents = reasoning

Evidence analyst, investigator and risk summary use an LLM, but every claim is grounded against stored evidence and labelled VERIFIED or INFERRED by code.

Humans = authority

Nothing changes until an approver accepts the exact plan hash. Nothing is pushed, merged or deployed — a verified fix becomes a local branch + PR.md.

Workflow

How one run flows end to end

LangGraph state machine: 9 agent nodes plus a pure router (record_decision). Routing is plain Python and every routing choice is written to the trace as a numbered decision.

One finding's journey

  1. Dev5 pinned the target repo; golden file + fixture lockfiles define what must be found.
  2. Dev2 copies the repo, resolves lockfiles without running scripts, Syft → SBOM, builds the graph with origin + integrity per node.
  3. Grype + OSV give a CVE on a transitive package; Dev4 detectors add typosquat / unpinned CI / tag-only image.
  4. Dev1 dedupes, attaches dependency paths, stores findings that cite evidence ids; the LLM explains them; grounding labels every claim.
  5. Dev4's scoring turns EPSS/KEV/reachability/exposure into an explainable 0–100 score and band.
  6. Remediation builds a plan (diff, expected drop, rollback, plan_hash); the gate pauses.
  7. Dev3 shows it in the approval view; the human approves for that hash.
  8. Dev2's sandbox patches a fresh copy, builds + tests with --network none, rescans, diffs the SBOM; Dev4 re-runs detectors + policy.
  9. Reporter writes the report; Dev3 shows before → after.

Remediation actions the plan can contain

Target values always come from evidence (G4.5), never from the model.

Risk score (Dev4's engine, called by Dev1's risk analyst)

S · severity (CVSS)weight 0.30
E · exploitability (EPSS pct, KEV)weight 0.25
R · reachability0.20 · import 0.6, called 1.0
P · production use0.15 · prod 1.0, dev 0.3
X · exposure0.10

+ up to 5 for a provenance modifier (cap 100) · KEV + reachable + prod forces at least High · confidence drops by 1 per unknown factor · every factor row carries its evidence ids. Result on Juice Shop: jsonwebtoken 0.1.0 via express-jwt 0.1.3 scores 98.17 (R = "called": jwt.verify in lib/insecurity.ts).

Guardrails G1–G7 (all enforced in code, each with tests)

G1 · secrets
Sensitive files refused (encryptionkeys/, *.pem, .env*…); 9 regex families redacted before LLM/log/report.
G2 · untrusted text
Package metadata and excerpts only inside <data> blocks; injection patterns raise a guardrail event.
G3 · tools
Per-agent allowlist, typed args, budgets (G3.6 sized per validation), no publish/push/merge tool, outbound host allowlist (G3.5).
G4 · grounding
Schema + one repair retry; evidence ids must exist; labels set by code; fix versions only from evidence.
G5 · approvals
Decision bound to plan_hash; reject/accept need a reason; heuristic findings never "upgraded"; 3 fails → escalate.
G6 · sandbox
Non-root, --cap-drop ALL, read-only root, no secrets, --network none for build/test.
G7 · audit
Every tool call, LLM call (with cache key), guardrail hit and decision in trace + append-only audit log.

How a tool call is guarded (the registry)

Key design decisions

  • Human gate = interrupt() only. On resume LangGraph re-runs the node from the top; keeping the node empty keeps plan_id stable. A separate pure router (record_decision) re-checks the approval.
  • LLM never creates facts. Score, band, confidence are computed in Python; the LLM writes the summary.
  • Record / replay. GUARDIAN_LLM_MODE=record stores answers in data/cache/llm; replay fails closed on a missing entry → offline demo with 0 network calls.
  • No key? Still finishes. Rule-based initial risk is used and the trace says which findings had no LLM review.
  • Crash-safe outputs. A finally block always writes graph, changes, run_summary and runs/LATEST.
  • Re-plan must differ. Remediation receives the previous ValidationResult and must choose another version/approach (e.g. Juice Shop express-jwt 8.5.1 broke tsc → re-plan).

Sandbox validation pipeline — the "verified" proof

Day-2 bugs found by real runs (each fixed with a regression test)

  • Sandbox: tests judged against the unpatched baseline; node test counts parsed; native addons (sqlite3) rebuilt inside the container on the target's Node version; multi-project npm apps prebuild subprojects.
  • Validator: patched copy's lockfiles start from discovery's resolution; dependency subtree of an upgrade is not "unexpected".
  • Remediation (patching): typosquat replacement also renames the imports; a plan may hold a real multi-file rename, never a partial one; plan-args bound follows MAX_PLAN_OPS.
  • Scanning: OSV purls match Grype's for every ecosystem; Maven in inventory; PyGoat Django app tests now run.

Proof & limits

What was shown to work — and what is honestly not done

Real runs

PyGoat58 packages, 470 findings, top 88.65 (django 3.2.18) → plan 4.2.26; sandbox Django tests 54/54.

Known limitations (disclosed in the docs)

  • Fixes are applied for npm and pip; Maven and others are scanned, scored and prioritised only.
  • Function-level reachability covers reviewed demo packages, not every advisory.
  • Built-image rescan is opt-in (GUARDIAN_IMAGE_BUILD=1) because it runs the target's Dockerfile with network on.
  • Rego rules are mirrored by a native Python evaluator; opa/conftest only if installed.
  • No Cosign verification of container images; popular-package list for typosquats is hand-written (342 npm names).
  • LLM explanations need a provider key or a recorded replay; otherwise rule-based risk is used and the run still finishes.
