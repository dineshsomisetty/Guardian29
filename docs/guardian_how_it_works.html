Guardian

An agentic software-supply-chain guardian. It looks at a repository, finds the risky parts of what the application is built from, ranks them, suggests a fix, waits for a person to approve it, proves the fix in a sandbox, and writes an evidence-backed report.

The one rule: tools produce facts, agents reason about them, humans approve changes. Every fact is stored as evidence; every AI sentence is labelled verified (matches evidence) or inferred by code, and unsupported sentences are removed.

1 · From repository to ranked risks

How a score is built

score = 100 × (0.40·Severity + 0.15·Exploitability + 0.20·Reachability + 0.15·Production + 0.10·Exposure) plus 5 points if provenance fails. Each factor is 0 to 1 and backed by evidence (CVSS, EPSS / KEV, whether your code calls the package, prod vs dev, network exposure). Levels: Critical ≥ 80, High ≥ 60, Medium ≥ 40, Low below. It is a ranking aid, not a probability of attack.

2 · From ranked risk to an approved fix

What a plan contains

  • the operations (upgrade, replace, remove, pin a CI action to a commit, pin an image to a digest, block, generate a lockfile)
  • a unified diff of exactly what would change
  • the target version and why it is safe (evidence)
  • expected risk reduction and a rollback note
  • a plan hash: the approval is bound to it

Two ways to decide

  • Decide all together: every suggested fix gets a decision, then all approved fixes are tested in one sandbox copy, the way they would be merged.
  • One at a time: submit each decision from its row; Validate now tests the approved ones straight away while the rest keep waiting.
  • Earlier verified fixes are applied underneath new ones, so the combination is what gets tested.

If a combined test fails, each fix is re-tested on its own to find the one that broke it, so a fix is never blamed for something another fix did. After three failed or rejected attempts a finding is handed to a person instead of being re-planned again.

Decisions: Remediation page in the UI, or guardian decide-batch / guardian validate-held on the CLI. Every decision is stored in approvals.jsonl with who, when and why.

3 · Proving a fix in the sandbox

The validator applies the approved plan to a fresh copy of the project and asks four questions: is the problem gone, does it still build, do the tests still pass, and did anything new appear?

How the verdict is decided

  • Tests are compared, by name, with the unchanged project (the baseline, cached). A test that already failed before is not blamed on the fix.
  • A newly failing test that checks an attack still works (deliberately vulnerable apps have these) is expected once the hole is closed: flagged, not counted.
  • Confidence is high only with build + tests + a clean re-scan.

Possible verdicts

verified problem gone, build and tests fine, nothing new
failed_build the patched project does not build
failed_tests tests that passed before now fail
still_imported stopped before the sandbox: code still uses it
regressed the re-scan found something new
mitigated risk reduced, vulnerable code stays

A verified fix becomes a local branch with a PR.md. Nothing is pushed or merged.

4 · The report

report.json (for tools) and report.html (for people) are built only from stored files, so the report cannot say more than the evidence. An interim report is written every time the run pauses for decisions after a fix was validated; the final one replaces it at the end.
